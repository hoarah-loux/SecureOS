## Physical/virtual addressing bugs — found AND fixed 2026-08-21

Getting `elf_load_process()` to actually pass took three separate physical/virtual addressing bugs, all the same root cause (a raw physical address used as a dereferenceable kernel pointer, correct only in specific boot phases/lucky ranges) but in three different places. All three found via GDB (`break handlers.c:35` after the prologue, print `faulting_va`/`error_code`/`fault_rip`, `info line *fault_rip`) — worth reusing that exact recipe for anything similar in the future.

1. **`buddy.c` free-list nodes**. `buddy_alloc_blocks`/`buddy_free_blocks` store and traverse their free lists as `struct buddy_node*`, but every address in there is physical (`buddy_init(0, ...)`, `pmm.c:182`), directly cast to a pointer and dereferenced (`block->next` at the old `buddy.c:65`, ~9 more sites). First caught at exactly that site: `faulting_va=0x7fcee000`, kernel read, not-present. It "worked" pre-transition purely because `entry64_mb2.asm` identity-maps the full low 4GiB there (confirmed directly, not inferred) — `pmm_init()`'s bootstrap `buddy_free_blocks` loop runs before `transition()`, so raw addressing is genuinely correct at that point. `transition()` then replaces that with a new table that only keeps a small kernel-image sliver identity-mapped plus the physmap — so a frame like `0x7fcee000` (near the top of a 2GB machine) stops being raw-dereferenceable, but `buddy.c` never knew the difference. **Fix**: `physmap_ready` flag (`vmm.h`/`vmm.c`, set `true` at the end of `transition()`) + a `node_kva()` helper in `buddy.c` (raw pre-flag, `phys_to_virt()` post-flag) wrapping every `->next` access. Considered and rejected: carrying the full 4GiB identity map through `transition()` instead — collides with `[0, HIGHER_HALF_BASE_)`, the same range user processes (including `/RING3.EXE`, loaded at `0x400000`) live in.
2. **`frame_metadata` itself**, same bug, different pointer. Set in `pmm.c` to `ALIGN_UP(kernel_end, 4096)` — also a raw low address, and its ~1MB array (for a 2GB machine) extends past the small sliver `transition()` preserves. Caught at `buddy.c:80` (`frame_metadata[block_index].flags = 1`), `faulting_va=0x1cff9dc`, kernel write. **Fix**: same pattern, one more helper — `fm_base()` (declared `buddy.h`, defined `buddy.c`), all 23 `frame_metadata[...]` sites in `buddy.c`/`pmm.c` renamed to `fm_base()[...]`.
3. **`create_vm_space()`'s new `kroot`-based kernel-entry copy** (from the upstream merge, companion-bug fix below) indexed `kroot` raw instead of translating it first — inconsistent with `the_walking_pager2`, which already established that `toptable`/`kroot` are *always* stored as physical addresses in this codebase and every consumer must `phys_to_virt()` them, unconditionally, no phase-gating needed (unlike bugs 1-2 above, this one isn't a pre/post-transition thing at all). Caught at `vmm.c:1830`, `faulting_va=0x7f7ff800`. **Fix**: one line, `phys_to_virt((uintptr_t)kroot)` before indexing.
4. **Not the same bug, but found in the same pass**: `elf_map_segments` (`loader.c`) was calling `vmm_map_page(..., space->pml4_ptr, ...)` — the *already-virtual* PML4 pointer — but `vmm_map_page`/`the_walking_pager2` expect a **physical** root table pointer (they `phys_to_virt()` it internally; confirmed as the general convention — all VMM functions expect physical addresses). Fixed: pass `space->pml4_phys_ptr` instead, matching `handlers.c`'s existing lazy-alloc call site.

All four confirmed via a full clean boot + `[ELF-LOAD] test elf_load_process: PASS (pid=1)`, with the rest of the self-test suite (PMM/VMM/FAT32/syscall/timer) still passing and boot continuing normally afterward.

## Ring3 kickoff bugs — found AND fixed 2026-08-22

Wiring the actual kickoff (`scheduler_init` → idle thread → `scheduler_add_ready` → `restore_context`) surfaced five more bugs, none related to the buddy-allocator class above. Found via the same GDB recipe plus targeted `printk` bisection when the panic path itself couldn't run (see bug 5). All boot-verified fixed — QEMU now reaches real ring3 execution (`CS=0x1B`, correct entry `RIP`, correct register state) with no panic/triple-fault up to that point.

1. **No idle-thread fallback.** `scheduler_set_idle_thread()` was declared (`hdr/scheduler.h:80`) but never defined; `scheduler_pick_next()` just returned `NULL` when the ready queue emptied (self-flagged in the code: `// this needs to be patched so that it runs the idle thread`). Needed because the kickoff's only ready thread (`RING3.EXE`) immediately blocks/spins after one instruction burst, emptying the ready queue on the very first preemption. **Fix**: implemented `scheduler_set_idle_thread()`; `scheduler_add_ready()` now no-ops successfully for the registered idle thread instead of queuing it (it's never queue-managed); `scheduler_pick_next()` falls back to it when the ready queue is empty.
2. **`BUDDY_MAX_PHYS` included non-RAM memory-map entries.** `pmm_init()` (`pmm.c`) computed `pmm_max_phys_end` (source for `BUDDY_MAX_PHYS`) as the highest `base+length` across **every** multiboot mmap entry type, not just usable RAM (type 1) — under UEFI/OVMF that includes a huge high-address MMIO/reserved aperture, ending up around 1TiB on this machine, versus the real ~2GB of RAM. The frame *bitmap* itself was already correctly clamped to a static 4GiB cap (`managed_phys_end`) for a separate reason — `pmm_max_phys_end` just never got the same treatment. This meant `BUDDY_MAX_PHYS`-derived VA math (kernel-asset region placement, right after the physmap) put new kernel-asset regions ~1TiB into virgin PML4 territory the page-table code had never touched, causing a walker fault. **Fix**: `pmm_init()` now clamps `pmm_max_phys_end` to the same `managed_phys_end` value used for the bitmap (`pmm.c`, right after that computation).
3. **`create_vm_space()` never mapped the kernel's own low-identity alias into new processes.** `transition()` maps the kernel image twice: once at its real low/physical VA (`_kernel_start`..`_kernel_end`, 2MB-aligned) and once at `KERNEL_IMAGE_BASE` (the higher-half alias) — but the kernel actually *executes* via the low alias (every RIP observed in this whole debugging session was a low address, never the higher-half one). `create_vm_space()`'s existing kernel-entry copy only handled PML4 slots `[256, 511]` (physmap + higher-half image) by sharing pointers — the low alias lives in PML4 slot 0, the *same* slot every process's own low/user address space lives in, so it can't be shared the same way; it was simply never carried over at all. Once a new process's CR3 went live, the kernel had no page to keep executing from. **Fix**: `create_vm_space()` now also calls `copy_mapping_dynamic_over_range()` (the same helper `transition()` uses) to replicate just the kernel image's own mapping into every new process's table.
4. **Cascading fallout from fix #3**: the helper chain fix #3 uses (`copy_mapping_dynamic_over_range` → `copy_mapping_dynamic` → `populate4k_into_table`/`populate2m_into_table` → `the_walking_pager`/`free_frame_for_new_page_structure_and_create_it`, all the non-`"2"` siblings) had never been exercised post-`transition()` before — only ever called from inside `transition()` itself, pre-physmap. Every one of them dereferenced physical intermediate-table addresses (PDPT/PD/PT pointers pulled from page-table entries) directly, with no `phys_to_virt()` translation — correct only pre-transition (identity-mapped), same bug class as the buddy-allocator bugs above, just never triggered until now. **Fix**: added a phase-gated `pt_kva()` helper next to `the_walking_pager()` (mirroring `node_kva()`/`fm_base()` in `buddy.c`) and applied it at every intermediate-table dereference across all four functions.
5. **Intermediate PML4/PDPT entries silently blocked ring3 access to sibling mappings.** Once fix #3 landed, `elf_map_segments` started failing to map `RING3.EXE`'s own segment — traced (via GDB register inspection at the fault, since `page_fault_handler` itself never got a chance to run — same chicken-and-egg as a broken kernel stack, but this time from a genuinely mapped-but-inaccessible page) to the PML4/PDPT entries covering the low address range having `US=0` (not user-accessible), even though the segment's own leaf PTE correctly had `US=1`. x86-64 ANDs the US bit across *every* level of the walk, not just the leaf — and the kernel's own low-identity mapping (correctly kernel-only, `US=0`) shares that same PML4[0]/PDPT[0] structure with anything else in the same low 1GB, since `populate4k_into_table`/`populate2m_into_table` (used by fix #3's copy) blindly inherited the *source* table's intermediate flags instead of promoting them. `spilt_page()` already had the right convention for this (forces `US=1` on newly-created intermediate levels for `virtual_address < HIGHER_HALF_BASE_`) but the two `populate*_into_table` functions didn't. **Fix**: both now OR in `PTE_US` on newly-created intermediate (non-leaf) entries for low/user addresses, leaving leaf permissions untouched — matches `spilt_page()`'s existing convention.
6. **Kernel stacks can't be lazily faulted in.** Separately (found before #2-#5, while first reproducing a triple fault from `restore_context`'s own GPR-push): the `#PF` handler runs on the *current* stack — CPL0 exceptions get no automatic TSS.RSP0 stack switch, that only happens on a ring3→ring0 privilege change. A fault caused by touching an unmapped *kernel* stack has nowhere safe to deliver the exception frame, so it immediately cascades into a double/triple fault instead of being handled. **Fix**: `create_thread()` (`t.c`) now eagerly backs the kernel stack region with real frames at creation time instead of leaving it lazy (user stacks stay lazy — ring3 faults *do* get the automatic TSS.RSP0 switch, so no chicken-and-egg there).

## Syscall gate crashes on first real ring3 use — found 2026-08-22, NOT fixed

With the kickoff working, `RING3.EXE`'s own `int 0x80` (its only way to prove itself — prints `hello from ring3` via `SYS_write`) triple-faults instead of reaching `syscall_handler`. This is the concrete next blocker.

Diagnosed so far (GDB, `break *0x20000cc` — the exact `int 0x80` instruction — plus a temporary `printk` at the top of `syscall_handler`):
- `syscall_handler` is **never reached** — confirms the crash is in interrupt delivery itself (CPU's automatic privilege-change stack switch, or `syscall_isr`'s own GPR-push prologue in `interrupts.asm`), not in C-level syscall logic (`sys_write`/`get_p`/`serial_write_char` were all inspected — no memory writes in that path that could explain what's below).
- The fault (`v=0e`, `error_code=0x0002` — supervisor write, not-present) is at `CR2=0x800fff8` (~128MB) every time — an address with no known connection to anything: not `RING3.EXE`'s own code/stack, not the kernel's low-identity image range (`[0, 0x1c00000)`), not the physmap-based kernel-asset stack region.
- `TSS.RSP0` was directly verified correct via GDB (`x/16xb &tss64`, byte-level, while broken at `*0x20000cc` under the live ring3 CR3) — reads back exactly `0xFFFF800100004000`, matching `first->_rsp_k`/`context->kernel_rsp`. So the target kernel stack for the privilege-change push is right; the fault isn't the stack itself as far as could be confirmed.
- IDT gate config (`idt.c:52-64`, `set_idt_entry`) for `SYSCALL_VECTOR` looks correct on inspection: standard 64-bit gate, offset split correctly across `offset_low`/`offset_mid`/`offset_high`, selector `0x08`, `ist=0`, type `0xEE` (present, DPL=3, interrupt gate) — matches `YIELD_VECTOR`/`EXIT_VECTOR`'s already-fixed encoding.
- Not yet checked: this is the **first time any DPL=3 IDT gate (`YIELD_VECTOR`/`EXIT_VECTOR`/`SYSCALL_VECTOR`, all `0xEE`) has ever been triggered by a real `int` instruction from real ring3 code** — every previous "test" of these vectors was `kernel.c`'s synthetic harness calling the C handler directly, never a genuine hardware-triggered gate transition. So this could just as easily be a bug that's always been latent in the gate mechanism itself, not something the kickoff work introduced.

## Merged upstream per-process fd tables — introduced a test regression (2026-08-21)

Merged `origin/master` (commit `2954581`, "added per proccess fd tables") cleanly, no file overlap with the ELF loader work, clean rebuild. But `sys_open`/`sys_write`/etc. (`fs_syscalls.c`) now call a new `get_p()` that requires `scheduler_this_cpu()` → `scheduler_current()` → `t->owning_proc` to all resolve to a real scheduled thread. `kmain`'s syscall smoke tests (`syscall_test_invoke` in `kernel.c`) call `syscall_handler()` directly with a synthetic trap frame — no scheduler ever initialized in that boot path — so `get_p()` returns `NULL` and both syscalls now return `-1` unconditionally.

Observed: `[SYSCALL] test write stdout: FAIL`, `test open /README.TXT: FAIL` (both passed before this merge); the read/lseek/close sub-tests get silently skipped as a knock-on effect (`kernel.c`'s test only runs them `if (open_ret >= 3)`).

**Not fixed yet** — undecided whether to give the test harness a fake/current process, or restructure when these tests run relative to scheduler init. Not something introduced by the ELF loader work, but surfaced by it since both this and `elf_load_process()`'s own success now depend on the same underlying scheduler/process plumbing being real.

## Bottom line

The scheduler is real now, not just code that compiles: `scheduler_init` → idle thread → a process built from a real ELF file → a genuine CR3 switch → real ring3 code executing, all boot-verified today (2026-08-22) via GDB register inspection, not inferred. Getting there required finding and fixing six more bugs beyond the four from the previous round (idle-thread fallback, `save_trap_frame` leak, `BUDDY_MAX_PHYS` including non-RAM firmware regions, the kernel's own low-identity mapping never being carried into new processes, the resulting cascade through four never-before-exercised page-table helper functions, and an intermediate-page-table US-bit bug blocking ring3 access to otherwise-correctly-mapped pages) — see "Ring3 kickoff bugs" above.

What's left, in order: **fix the syscall-gate crash** (`RING3.EXE`'s `int 0x80` triple-faults before reaching `syscall_handler` — see that section above, this is what stands between here and an actual `hello from ring3` on the serial log) → thread the shell/console loop as its own kernel thread so it survives past the kickoff (currently `kmain`'s tail — console init + interactive shell — is unreachable once `restore_context` hands off; the already-built-but-dead blocking `SYS_getkey_wait` path, real for the first time now that the scheduler runs, is the natural thing for it to use instead of a busy-poll) → fix the `sys_open`/`sys_write` test-harness regression from the fd-table merge → fix `init_proc.c` name mismatch and give it a real body → make protection-fault paths kill the process instead of `panic()` → write minimal `src/stdlib` (malloc/free/memcpy/string/file wrappers + crt0, note `memcpy`/`memset`/`memcmp` already exist in `hdr/string.h`) → write `src/userland` doom-generic backend (framebuffer blit + arrow keys needed first, `load_file`'s `kmalloc` cap needs its own large-allocation path for a WAD).
