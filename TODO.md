## Build system was silently incomplete (found + fixed 2026-08-21)

`src/boot/Makefile`'s `KERNEL_SRCS`/`ASM_SOURCES` never included `proc/sched/*.c` (scheduler, queues, context), `proc/ds/*.c` (p.c, t.c), `proc/init_proc.c`, or `context_switch.asm` — the entire scheduler/proc subsystem had never been compiled as part of a real build, let alone linked. Now wired in. Fixing that surfaced (and required fixing) several dormant bugs that only show up once everything actually compiles together:

- [x] `p_states.READY` collided with `queue_type.READY` (same enum value name, different enums) — renamed to `READY_P` (`p.h`).
- [x] `vm_space` used before declared in `vmm.h` — forward-declared + struct moved above first use.
- [x] `k_root`/`active_pml4_phys`/`active_space` were non-`extern` globals declared in a header (`vmm.h`) — multiple-definition at link time in every TU that included it. Made `extern`, single definition moved to `vmm.c`.
- [x] `p.c` had its own unrelated `uintptr_t *k_root` global that collided by name with vmm's `k_root` — renamed to `proc_kernel_root`.
- [x] Circular include `t.h` ↔ `context.h` — order-dependent whether `thread` was visible when `context.h` needed it. Broken by having `context.h` forward-declare `struct thread` instead of including `t.h`.
- [x] `vmm.c` `mmap()` assigned `void*` to `uintptr_t` with no cast — added cast.
- [ ] `context.c` `save_trap_frame()` leaks memory on every call (`kcalloc`s a fresh `context`/`trap_frame` per trap instead of reusing the thread's existing one, per its own comment at line 125) — will exhaust the heap fast once a process is actually taking timer ticks/syscalls under a real scheduler.

## Buddy allocator: physical/virtual address bug (found 2026-08-21, NOT fixed — reverted, see below)

`buddy_alloc_blocks`/`buddy_free_blocks` (`buddy.c`) store and traverse their free lists as `struct buddy_node*` — but every address in there is a **physical** address (`buddy_init(0, ...)` is called with base `0`, `pmm.c:182`), directly cast to a pointer and dereferenced (`block->next` at `buddy.c:65`, same pattern ~6 more places). This kernel is higher-half; a physical address is not a valid kernel-virtual pointer without going through `phys_to_virt()` first.

**Confirmed via GDB**: calling `elf_map_segments()` (see above) — the first real, non-bootstrap caller of `pmm_alloc_frame()` in this project's history — faults at `buddy.c:65`, `faulting_va=0x7fcee000`, kernel-mode read, not-present. It "worked" until now purely by luck: `create_vm_space`'s own PML4 allocation happens to grab an early low-address frame that's still identity-mapped as a `transition()` boot-compatibility leftover; my loader's later allocations landed near the top of RAM (`0x7fcee000` with `-m 2048`), well outside that lucky range, and crashed for real.

**This is not a one-line fix.** `pmm_init()`'s bootstrap population (a `buddy_free_blocks` loop over every managed frame) runs **before** `vmm_init()`/`transition()` — before the physmap exists at all (`kernel.c:290` vs. `294`/`313`). At that point raw physical dereferencing is what actually works (early boot page tables identity-map a wide low range); a blanket `phys_to_virt()` wrap breaks *that* phase instead (tried it — kernel hung/silently reset with zero output right after `[VMM] initializing PMM/VMM test path`, worse than the original bug, reverted immediately). A real fix has to handle both regimes correctly:
- pre-transition: raw physical works, physmap doesn't exist yet
- post-transition: physmap works, raw physical only works for the small preserved-identity low range

Options to weigh next time: defer buddy's bootstrap free-list population until after `transition()`, or make the node-dereference translation conditional on whether the physmap is live yet (e.g. a boot-phase flag). Needs a decision before touching the code again, not another blind patch.

**Practical effect right now**: this is the **only** remaining blocker on calling `elf_map_segments`/`elf_load_process`/`create_vm_space` for real (anything that calls `pmm_alloc_frame` outside the handful of early frames pmm/vmm allocate for themselves during boot) — both companion bugs above are now fixed upstream. The `kmain` test block that exercised this has been removed again (it panicked every boot, burying the console/shell/keyboard tests after it) — `buddy.c` is back to its original, pre-existing-bug-but-boot-safe state. `loader.c`'s new functions are still written and compile clean (rebuilt clean after merging the upstream fixes too), just genuinely unverified beyond their own internal `memcmp` self-check.

## Doom-generic port blockers (surveyed 2026-08-21, none started)

- [x] **Timer IRQ0 is masked** — fixed 2026-08-21. `pic_init_for_keyboard()` now unmasks it at boot (`pic.c:101-102`); removed the redundant later unmask call that used to sit at `kernel.c:557` ("interactive stage"). Boot-tested in QEMU: full self-test suite still passes with the timer live the whole run, no hang/crash. `timer_ticks`/`timer_ticks_get()` now genuinely count — ready to back `DG_GetTicksMs`/`DG_SleepMs`.
- [x] ~~`kmalloc` capped at 4096 bytes~~ — **not actually a blocker**: Doom runs as a usermode process and will use its own `malloc` (backed by `SYS_brk`/`SYS_mmap`, see stdlib item below), never `kmalloc`. Investigated wiring the buddy allocator into `kmalloc` anyway but backed it out — wrong layer, `kmalloc` stays slab-only/4KB-capped as kernel-internal allocator. `buddy.c` is already live in production, just not for this.
- [ ] **`load_file()` will fail on any file over 4KB** — `loader.c:19` calls `kmalloc(file.entry.file_size)`, still capped at 4096. A Doom WAD (several MB) can't be loaded this way. Fix belongs in the loader (stream/mmap the file, or give the loader its own large-allocation path), not in `kmalloc` generally.
- [ ] **No framebuffer blit/putpixel API exposed** — `fb_putpixel` (`framebuffer.c:4-26`) is `static`; only rect-fill/text helpers are public. `DG_DrawFrame` needs a raw pixel-buffer blit. Framebuffer address/resolution/pitch/bpp are available (`kmain` parses the multiboot2 tag) but not exposed as a reusable API outside `kmain`.
- [ ] **No arrow-key / extended-scancode handling** — `keymap_base`/`keymap_shift` (`keyboard.c:12-50`) have no entries for arrow keys (0x48/0x50/0x4B/0x4D), and there's no 0xE0 extended-prefix handling at all, so arrow key presses are silently dropped as two separate unmapped scancodes. Doom's directional/menu input is unusable as-is.

## Bottom line

Hardware scaffolding (GDT/TSS/page bits, syscall gate, lazy-alloc page fault path, scheduler/proc/thread data structures, ELF segment loader) is real and — as of today — actually compiles and links for the first time. The remaining blockers are no longer "missing code" so much as a short chain of specific, identified bugs standing between here and a running usermode process:

Order: **fix the buddy allocator's physical/virtual addressing bug** (see above — the last remaining blocker, everything else on the critical path is now done) → re-verify the ELF loader end-to-end (reinstate a `kmain` test block calling `elf_load_process` once the buddy fix lands) → call `scheduler_init`/`elf_load_process`/`scheduler_add_ready` + an initial `scheduler_pick_next`+`restore_context` kickoff from `kmain` → fix `init_proc.c` name mismatch and give it a real body → make protection-fault paths kill the process instead of `panic()` → fix the `save_trap_frame` leak → write minimal `src/stdlib` (malloc/free/memcpy/string/file wrappers + crt0, note `memcpy`/`memset`/`memcmp` already exist in `hdr/string.h`) → write `src/userland` doom-generic backend (framebuffer blit + arrow keys needed first, `load_file`'s `kmalloc` cap needs its own large-allocation path for a WAD).
